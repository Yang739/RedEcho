# RedEcho 小程序架构设计

> 版本：v1.0 ｜ 技术栈：微信小程序（原生）+ 微信云开发 + 腾讯云 IM + AIGC
> 适用范围：游客端、工作人员端（场务 / 演员），含实时互动、AIGC 明信片、周边商城、硬件打印。

---

## 1. 架构总览

RedEcho 采用 **「小程序原生前端 + 云开发 BFF（Backend For Frontend）」** 的轻后端架构：前端只做渲染与交互，所有业务规则、数据聚合、第三方调用（IM / AIGC / 支付 / 短信）都收敛到**云函数层**，避免在小程序端暴露密钥、也降低端上逻辑复杂度。

```
技术栈总表
┌────────────────┬──────────────────────────────────────────┐
│ 表现层          │ 微信小程序原生 (WXML/WXSS/JS)，分包加载    │
│ 逻辑/服务层     │ service 层统一封装云函数调用 + 全局状态    │
│ 接入层(BFF)     │ 云函数（Node.js），路由网关 + 业务函数    │
│ 数据/存储       │ 云数据库(NoSQL) + 云存储 + 云调用         │
│ 实时通道        │ 腾讯云 IM 群组（投票/台词/表情/短片）     │
│ 智能能力        │ 文生图 API(明信片) + 大模型 API(台词)     │
│ 硬件            │ 蓝牙打印机 / 云打印服务（抽象适配层）      │
│ 支付/触达       │ 微信支付(预留) + 短信验证码               │
└────────────────┴──────────────────────────────────────────┘
```

---

## 2. 分层架构与职责

| 层 | 职责 | 关键产物 |
|---|---|---|
| **View 层** | 页面与组件渲染、交互反馈 | `pages/`、`packages/`、`components/` |
| **Logic 层** | 页面业务逻辑、表单校验、本地状态 | 各页面 `.js` |
| **Service 层** | 统一调用云函数、错误归一化、重试、缓存 | `services/*.js`、`utils/request.js` |
| **Global 层** | 登录态、用户信息、主题、字号偏好 | `app.globalData` + `store/` |
| **云函数 BFF 层** | 鉴权、参数校验、DB/IM/AIGC 编排、限流 | `cloudfunctions/*` |
| **基础能力层** | 云数据库 / 云存储 / IM / AIGC / 支付 | 云开发控制台资源 |

**数据流原则**：端上不直接连数据库；所有读写经云函数。实时类走 IM 推送，非实时类走云函数 request-response。

## 3. 目录结构与分包设计

```
RedEcho/
├── app.js / app.json / app.wxss      # 全局配置（云初始化、分包、tabBar）
├── config.js                         # 环境ID、域名白名单、主题常量
├── services/                         # 服务层：按业务聚合云函数调用
│   ├── auth.js                       #   登录/双因子
│   ├── show.js                       #   场次/环节/投票
│   ├── create.js                     #   明信片/AIGC
│   ├── mall.js                       #   商品/订单/核销
│   └── dash.js                       #   数据看板
├── store/                            # 轻量全局状态（pub/sub）
│   ├── user.js                       #   登录态
│   └── live.js                       #   当前演出实时状态
├── components/                       # 复用组件（投票器/弹幕/星级/打印面板…）
├── utils/                            # request.js、im.js、敏感词、日期、防抖
├── pages/        (主包·tabBar)       # 首页/演出/创作/我的（轻壳）
├── packages/
│   ├── show/     (分包A·演出)        # room(房间)/review(回顾)/staff(场务台)
│   └── create/   (分包B·创作)        # generate(生成)/mylist(我的明信片)/scenes
├── cloudfunctions/                   # 云函数根目录（每个函数独立目录+package.json）
└── images/                         # tabBar图标、占位图
```

**分包策略**
- 主包仅放 4 个 tabBar 入口 + 全局组件/工具（微信限制：tabBar 页必须在主包）。
- 重交互页进分包：`packages/show`（演出房间/回顾/场务台）、`packages/create`（明信片生成/历史）。
- 配置 `preloadRule`：进入「演出」tab 时预载 `packages/show`；进入「创作」tab 时预载 `packages/create`，消除跳转白屏。
- 独立分包（independent）留给「工作人员端」单独入口，可被场务/演员从二维码直进，互不拖累游客端体积。

## 4. 核心模块设计

### 4.1 统一服务层（Service）
`utils/request.js` 封装 `wx.cloud.callFunction`，统一：
- 注入 `traceId`、登录态；
- 错误码归一（`code !== 0` 弹 toast / 跳转登录）；
- 失败重试与降级（IM 推送失败时轮询 `pollResult` 兜底）。

### 4.2 演出状态机（高优先级）
防并发、防误操作的严格状态流转：

```
[草稿] --场务发布--> [即将开始] --到点/手动--> [进行中]
   |                      |                        |
   | 取消                 | 取消                   | 环节循环：
   v                      v                        |  (开始投票→结束)
[已取消]<----------------[已结束]<-----------------+  (播放短片)
                                               (答题活动)
```
- 状态字段落在 `shows.status` 与 `show_segments.status`；
- 所有状态变更由云函数 `showControl` 单点串行执行，用云数据库事务/原子更新防止竞态；
- 分支锁定（`show_branch_log.locked`）后不可再改。

### 4.3 实时互动（腾讯云 IM 群组）
- 每个场次一个 IM 群组（`shows.im_group_id`）：游客 + 演员 + 场务同在群内。
- **下行（场务→游客）**：`pollStart / segmentStart / videoPush / branchLock` 由云函数调用 IM REST 推群消息，游客端监听渲染投票器/短片/环节切换。
- **上行（游客→场务）**：`pollVote / emotionSend` 经云函数写 DB 并广播，结果页订阅刷新柱状图/弹幕，大屏订阅 `emotionStats`。
- **演员台词**：`aiLineGenerate` 调用大模型流式输出，结果经 IM 私信推演员端。
- SLA：指令→游客端 < 1s，投票响应 < 500ms。

### 4.4 权限与鉴权
- 游客：微信 openid 身份，端上 `AppID` + `code2Session`。
- 工作人员：手机号 + 密码/验证码登录；敏感操作（发起投票、核销、锁定分支）需 `staff_verified` 双因子二次验证。
- 云函数统一中间件校验 `role` + `staff_types`，越权返回 `403`；绝不信任端上传入的用户身份，身份以 `cloud.getWXContext().OPENID` 为准。

### 4.5 AIGC 双引擎
- **明信片（文生图）**：`postcardGenerate` 组装 Prompt（场景模板 + 名言 + 用户头像）→ 调文生图 API → 后处理（合成字体/水印/留白）→ 存云存储返回 URL，< 10s。
- **台词（LLM）**：`aiLineGenerate` 结合「当前环节 + 投票趋势 + 角色背景」生成多条备选，支持流式与 TTS 预览。
- 手动输入名言走 `sensitiveCheck` 敏感词过滤后再入库。

### 4.6 打印硬件抽象层
`utils/printer.js` 提供统一接口：`printImage(fileID)`，内部适配两种实现：
- 蓝牙打印机（小程序蓝牙 API，现场直连）；
- 云打印服务（上传云存储 + 调打印厂商 API）。
无硬件时降级为「保存相册 / 分享」。

### 4.7 数据可视化
投票实况、运营看板用 ECharts（小程序版 `ec-canvas` 组件）渲染柱状图/排行榜；大屏端订阅 IM 实时刷新。

## 5. 云函数设计规范

- **职责划分**：基础函数单函数单职责（`pollVote`、`postcardGenerate`…）；可选 `gateway` 统一做鉴权/路由，降低冷启动与维护成本。
- **自包含**：每个云函数为独立目录，公共初始化（wx-server-sdk、cloud.init、db、getOpenid、ok/fail 助手）已**内联到各函数顶部**。原因：微信云开发「上传并部署」只打包单个函数目录，无法跨目录引用共享模块，故不引入 `common/` 共享库（详见 `cloudfunctions/README.md`）。
- **错误码**：统一 `{ code, msg, data }`，`0` 成功，4xx 业务/权限，5xx 系统。
- **限流与安全**：云函数层对投票/生成做频率限制；AIGC 调用加配额与降级。

---

## 6. 安全与性能

- **防越权**：身份以云端 `OPENID` 为准；工作人员操作二次验证。
- **内容安全**：用户文本（名言/短语）调 `security.msgSecCheck` + 本地敏感词库。- **性能**：分包预载 + 骨架屏；列表分页；云数据库建必要索引（`user_id`、`show_id`、`created_at`）；图片走 CDN/压缩。

---

## 7. 工程化与质量

- 组件化：`components/` 沉淀投票器、弹幕、星级、打印面板等。
- 配置管理：`config.js` 区分 dev/prod；密钥只存在于云函数环境变量。
- 可观测：云函数日志 + 自定义监控告警（AIGC 耗时、IM 推送失败率）。
- 适配：全局字号缩放（中老年友好），按 `systemInfo` 做机型适配。

## 9. 关键权衡

- **IM vs 云数据库实时监听(watch)**：IM 更适合「一对多广播 + 大屏 + 私信台词」，且延迟可控；watch 适合简单单文档。本项目选 IM 作为实时主干，watch 仅作兜底。
- **云开发按量成本**：免费额度覆盖开发测试；上线后对 AIGC/IM 调用量做配额与缓存（如热门卡片、名言库预热），控制费用。
- **原生 vs 跨端框架**：已定原生 + 云开发，契合需求且迭代成本低；若未来要多端再评估 Taro 迁移成本。

## 10. 当前实现范围（与 M2 规划的偏差）

> 本节记录截至本版本已落地的 MVP 与原始架构规划的差异，便于回归时对齐。

- **资料卡片内容源（偏差）**：M2 规划中首页卡片由云函数 `getHomeFeed` 从云数据库返回；**当前实现改为前端直读本地内容源 `services/resources.js`**（湖南主题红色史料，约 22 条 / 6 分类），`services/api.js` 的 `getHomeData` 双模式（真云 / mock）均直接返回该本地数组，**无需灌库**，降低联调成本。后续如需运营可后台维护，再将内容迁移至云数据库并由 `getHomeFeed` 返回。
- **首页推荐规则**：从全库**随机抽 3 张**卡片，不区分分类；分类筛选仅在「资料中心」(`pages/resource/list`) 内出现。
- **未实现项（本版）**：资料卡片的**收藏 / 阅读积分**仍为后续扩展，未接入云函数与积分体系（详见《需求文档》3.1）；**短视频**已在详情页加入占位（相关宣传片，待填内容）；**点赞功能已取消**，不再规划。
- **本版已落地（增量）**：资料卡片详情页加入「相关宣传片」占位；「我的阅读」本地阅读历史已在 `pages/read/read` 落地（入口在「我的服务」菜单，记录存于 `wx` 本地存储，无需后端，见 `services/readHistory.js`）。
- **首页红色足迹**与「我的阅读」（`pages/read/read`）共用 `readHistory` 本地数据源，保证两端阅读记录同步；首页仅展示最近 3 篇，点「全部 ›」跳转列表页。
- **首页为你推荐**优先推送未读资料（基于 `readHistory` 标记），全部读完则继续随机。
- **用户登录与积分体系**：当前游客端以本地资料浏览为主，IM 实时演出、商城核销、AIGC 明信片等 M3–M5 能力尚未在本仓库代码层落地。
